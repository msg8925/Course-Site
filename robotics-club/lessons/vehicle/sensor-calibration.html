Calibrating Sensors to the Competition Surface

Section focus: Robotic Vehicle — Line Sensor Subsystem — Lesson 4.1.4  |  Duration: ~45 minutes

Builds on: Lessons 4.1.2 (sensor array) and 4.1.3 (LCD readout). This lesson turns raw sensor numbers into a reliable per-sensor threshold.

Learning Objectives

By the end of this session, you will be able to:

  • Explain why a single hardcoded threshold value is unreliable across multiple sensors
  • Record each sensor's light and dark readings on the actual competition surface
  • Calculate an individual threshold for each sensor
  • Store and use per-sensor thresholds in your program

1. Why One Shared Threshold Isn't Good Enough

It's tempting to pick a single number (say, 500) and use it for every sensor. In practice, small manufacturing differences between individual IR LEDs and phototransistors, slightly uneven mounting height, and even minor differences in ambient light across the sensor row all mean that each sensor's "light" and "dark" readings can genuinely differ from its neighbours'. A threshold that works perfectly for one sensor may misread another entirely.

The competition surface itself matters too. A threshold calibrated on a coffee table at home may not transfer reliably to the actual competition floor and tape, especially if lighting conditions differ (fluorescent lights, sunlight through windows, etc). Always calibrate on the same surface — or as close to it as possible — that you'll actually compete on.

2. Recording Light and Dark Values, Per Sensor

1Set up your test rig

Using the LCD or Serial Monitor readout from Lesson 4.1.3, position the sensor array over the light-coloured surface (away from any tape) and record all 5 readings.

2Record dark readings

Move each sensor, one at a time, directly over the tape, and record its reading in that position.

A simple, effective threshold for each sensor is the midpoint between its own light and dark readings — this naturally adapts to each sensor's individual behaviour rather than assuming they're identical.

3. Storing Per-Sensor Thresholds in Code

const int sensorPins[5] = {A0, A1, A2, A3, A4};
int sensorReadings[5];

// Replace these with YOUR actual calculated midpoints
const int thresholds[5] = {500, 480, 510, 495, 505};

bool isOnLine[5];  // true if that sensor currently sees the dark tape

void setup() {
    Serial.begin(9600);
}

void loop() {
    for (int i = 0; i < 5; i++) {
        sensorReadings[i] = analogRead(sensorPins[i]);
        isOnLine[i] = sensorReadings[i] > thresholds[i];
    }

    for (int i = 0; i < 5; i++) {
        Serial.print(isOnLine[i]);
        Serial.print(" ");
    }
    Serial.println();

    delay(100);
}

This program now reports a clean true/false per sensor, individually calibrated — exactly the information your line-following logic in Lesson 4.3.1 will actually need, rather than raw numbers requiring interpretation.

Looking ahead: the isOnLine[] array built here is exactly what Lesson 4.3.1's decision logic will read from — this lesson's whole purpose is producing that clean, reliable array.
Try it yourself:
  1. Record real light and dark readings for every sensor on your actual test surface, and calculate each threshold.
  2. Update your code with your real threshold values and confirm each sensor correctly reports true/false as you move it over the tape.
  3. Test what happens if you recalibrate in a room with different lighting — do your thresholds still work well, or do they need adjusting?
  4. Challenge: rather than hardcoding thresholds, write a short calibration routine that runs once at startup, asking you (via Serial or LCD prompts) to place the vehicle on light then dark surfaces, automatically recording the readings and calculating thresholds itself.
