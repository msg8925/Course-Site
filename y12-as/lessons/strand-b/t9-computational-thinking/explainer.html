01

Why this matters

Before you can write an algorithm for a problem, you have to actually understand the problem — and complex, real-world problems are rarely understandable all at once. Computational thinking is the set of habits that turns a messy, complicated problem into something you can actually design a solution for.

Three of the most useful habits are decomposition (breaking a problem into smaller pieces), abstraction (ignoring the detail that doesn't matter), and pattern recognition (spotting when a new problem is similar to one you've already solved). You'll use all three, usually together, every time you design a non-trivial algorithm for Paper 2.

02

Decomposition

Decomposition means breaking a complex problem down into a series of smaller, more manageable sub-problems. Each sub-problem is easier to think about, design, code, and test on its own than the whole problem would be — and sub-problems can often be tackled by different people, or reused elsewhere.

Worked example — a class attendance register

Manage a class attendance register
Add a new student to the register
Mark a student present or absent for today
Calculate a student's overall attendance percentage
Count total sessions recorded
Count sessions marked present
Divide and convert to a percentage
Display the register for a given day
Save and load the register data

Notice that decomposition can happen in layers: "calculate attendance percentage" is itself broken down further into three smaller steps. You keep decomposing until each piece is simple enough to design directly.

Worth noticing

A good sub-problem is one you could hand to a classmate and have them solve it without needing to understand the rest of the system.

Problem: design a program that runs a simple online pizza ordering system for one restaurant.
Compare with a model decomposition

There's no single correct answer — but a reasonable decomposition might include:

  • Display the menu and prices
  • Take the customer's order (items and quantities)
  • Validate that the chosen items exist on the menu
  • Calculate the order total, including any delivery charge
  • Take payment details
  • Confirm the order and give an estimated delivery time
  • Send the order to the kitchen / delivery system

How many of these did you already have? Did you think of any reasonable sub-problems that aren't on this list? That's fine — decomposition isn't a single "correct" tree, as long as each piece is genuinely smaller and more manageable than the whole.

04

Abstraction

Abstraction means removing the detail that isn't relevant to the problem you're solving, so you're left with a simplified model containing only what actually matters. Real-world things and situations always contain far more detail than any one program needs.

Worked example — modelling a "Book" for a library system

Kept (relevant to a library system)
Title, author, ISBN, availability status, due-back date
Removed (irrelevant to a library system)
The exact font used inside, the smell of the paper, which shop originally sold it

A book has almost unlimited physical detail. A library system only needs the details relevant to lending it out and finding it again.

Common mistake

Relevance isn't fixed — it depends on the purpose of the system. A rare-books archive tracking physical condition for restoration would care about paper damage and cover material. Always ask "relevant to what?", not just "relevant?".

06

Pattern recognition

Pattern recognition means noticing similarities between a new problem (or part of one) and something you've already solved, so you can reuse or adapt an existing approach instead of starting from scratch.

Worked example — area calculations

"Calculate the area of a rectangle" and "calculate the area of a triangle" look like different problems, but both follow the same underlying pattern: take some measurements as input, apply a formula, output the result. Recognising the shared pattern means you can design one general structure and simply swap the formula.

Worked example — searching

Finding a student's name in a register, a product code in a catalogue, and a word in a dictionary are all completely different contexts — but the underlying algorithm is the same "search" pattern: check items one at a time until you find a match or run out of items to check.

08

Bringing it together

In practice, these three skills work as a team. Imagine designing a system to manage a small gym's class bookings:

  • Decomposition splits the problem into sub-problems: list available classes, take a booking, check the class isn't full, cancel a booking, send a reminder.
  • Abstraction decides what to model for a "class": name, time, instructor, maximum capacity, current bookings — and leaves out irrelevant detail like the studio's paint colour.
  • Pattern recognition notices that "check the class isn't full" is really the same pattern as "check a cinema seat is available" or "check a hotel room is free" — a general availability-checking pattern you may already know how to code.

Only once all three have done their work does it make sense to start writing pseudocode.

09

Key takeaways

  • Decomposition: break a complex problem into smaller sub-problems, and keep decomposing sub-problems that are still too big.
  • Abstraction: keep only the detail that's relevant to your system's purpose, and discard the rest — relevance depends on what the system is actually for.
  • Pattern recognition: look for similarities to problems you've already solved, so you can reuse or adapt existing approaches.
  • These three skills are used together, and come before writing pseudocode or code — they're how you turn a vague, complicated problem into something you can actually design an algorithm for.
