C

Decomposition case studies

Break each problem into at least four sub-problems, then compare with a model answer.

7

A school wants a simple program to manage lunch orders: students choose a meal option, the system records their choice, calculates the total cost for the day across all students, and produces a summary for the kitchen.

Show a model decomposition
  • Display the available meal options to students
  • Record each student's choice
  • Validate that a valid option was chosen
  • Calculate the total cost per student
  • Calculate the total cost across all students
  • Produce a summary report for the kitchen (e.g. grouped by meal option)

Any reasonable breakdown into genuinely smaller sub-problems is acceptable — there's no single correct tree.

8

A fitness app needs to track a user's daily steps, calculate calories burned, and show weekly progress against a step-count goal.

Show a model decomposition
  • Record the daily step count
  • Calculate calories burned from steps, using a formula
  • Store daily records across the week
  • Sum steps across the week
  • Compare the weekly total against the user's goal
  • Display progress, e.g. as a percentage of the goal achieved

E

Exam-style question

A longer, multi-part question bringing all three skills together.

13

A company wants software to manage a car rental fleet: customers book a car for a date range, the system checks availability, calculates the rental cost (based on car type and number of days), and updates the fleet's availability.

(a) Suggest one way decomposition could be used when designing this system.
(b) Suggest one piece of information that would be relevant to model for a "Car" in this system, and one that would be irrelevant. Justify both choices.
(c) Suggest one existing pattern, from a different type of problem, that part of this system might reuse.

Show model answer

(a) The system could be broken into sub-problems such as: checking car availability for the requested dates, calculating the rental cost, processing the booking, and updating the fleet's availability record. (Any reasonable decomposition into smaller, manageable sub-problems is acceptable.)

(b) Relevant: the car's type/category or daily rental rate — needed to calculate the cost. Irrelevant: e.g. the car's paint colour, or the name of the previous renter — neither is needed to check availability or calculate cost.

(c) Checking whether a date range is available is the same underlying pattern used in many other booking systems — for example checking hotel room availability, or checking whether a library book is currently out on loan. Recognising this means the same "check for a clash against existing bookings" algorithm structure can be reused.
