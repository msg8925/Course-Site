01

Why bother with procedures?

Every program you've written so far in this course has been one continuous block of statements. That works fine for short pseudocode, but real programs quickly become long, repetitive, and hard to follow. A procedure is a named, self-contained block of statements that you define once and can call — run — as many times as you like from anywhere in the program.

Splitting a program into procedures (and, from tomorrow's lesson, functions) gives you:

  • Reuse — write the logic once, call it from ten different places instead of copying and pasting it ten times.
  • Readability — a well-named procedure call, like CALL DrawBorder(), tells the reader what happens without them needing to read the details.
  • Easier maintenance — fix a bug or change the logic in one place, and every call benefits.
  • Easier testing — a procedure can be tested in isolation from the rest of the program.

A procedure on its own is useful, but a procedure that can be told what to work on — via parameters — is far more useful. That's the focus of this lesson.

02

Defining and calling a procedure

A procedure is defined with the PROCEDURE keyword and closed with ENDPROCEDURE. Without any parameters, it looks like this:

pseudocode
PROCEDURE DrawBorder()
   OUTPUT "----------"
ENDPROCEDURE

To run it, you call it by name, using the CALL keyword:

pseudocode
CALL DrawBorder()
CALL is a complete statement A procedure call sits on its own line and does not produce a value that can be used in an expression — you can't write Total ← CALL DrawBorder(). That distinction matters more once functions arrive tomorrow, which do return a value and are called differently.

Most procedures aren't this rigid — they need to work on whatever data they're given. That's what parameters are for.

03

Parameters and arguments

A parameter is a named placeholder listed in a procedure's definition. An argument is the actual value supplied when the procedure is called. It's easy to blur the two together, but the distinction is worth keeping straight for exam answers:

TermWhere it appearsExample
ParameterIn the procedure's definitionSize in PROCEDURE Square(Size : INTEGER)
ArgumentIn the call100 in CALL Square(100)

A procedure with parameters is defined by listing each one, with its data type, inside the brackets:

pseudocode
PROCEDURE Square(Size : INTEGER)
   FOR Side ← 1 TO 4
      CALL MoveForward(Size)
      CALL Turn(90)
   NEXT Side
ENDPROCEDURE

CALL Square(100)

When the procedure is called, the arguments are matched to the parameters strictly by position — the first argument fills the first parameter, and so on — and each argument must be of the correct data type. Calling Square("large") would be invalid, since Size expects an INTEGER.

Multiple parameters A procedure can take as many parameters as it needs, separated by commas: PROCEDURE MoveTo(X : INTEGER, Y : INTEGER), called as CALL MoveTo(50, 120).
04

Passing by value

When Square(100) runs, what actually happens to the parameter Size? By default, the procedure receives its own private copy of the argument's value. This is called passing by value, and it's the default in Cambridge pseudocode — if you don't say otherwise, by value is assumed.

Because the procedure only ever sees a copy, anything it does to the parameter has no effect on the variable back in the calling code:

pseudocode
DECLARE x : INTEGER
x ← 5
CALL DoubleNum(x)
OUTPUT x   // still outputs 5

PROCEDURE DoubleNum(num : INTEGER)
   num ← num * 2   // only changes the local copy, num
   OUTPUT num       // outputs 10
ENDPROCEDURE

Doubling num inside the procedure doubles the copy — x back in the calling program is untouched. You can write BYVAL explicitly before a parameter to make this obvious to a reader (PROCEDURE DoubleNum(BYVAL num : INTEGER)), but it changes nothing about how the procedure behaves, since by value is already the default.

05

Passing by reference

Sometimes you want a procedure to change a variable that belongs to the calling code — for example, a procedure that swaps two values only makes sense if it can actually reach into the caller's variables. For this, precede the parameter with BYREF. Instead of a copy, the parameter becomes another name for the same variable — so changes made inside the procedure are changes to the original.

pseudocode
DECLARE x : INTEGER
x ← 5
CALL DoubleNum(x)
OUTPUT x   // now outputs 10

PROCEDURE DoubleNum(BYREF num : INTEGER)
   num ← num * 2   // changes x itself, since num IS x
ENDPROCEDURE

06

Local and global scope

The parameter num only exists inside DoubleNum — it's a local variable, created when the procedure is called and destroyed when it finishes. Trying to OUTPUT num from the main program, outside the procedure, would be invalid: num doesn't exist there.

A variable declared in the main body of the program, outside any procedure, is a global variable — it exists for as long as the program runs and can be read from anywhere, including inside procedures. This matters for parameters specifically:

  • Parameters and any variables DECLAREd inside a procedure are local to that procedure.
  • Two different procedures can each safely use a local variable called Temp without clashing — they're entirely separate variables that happen to share a name.
  • Relying on global variables inside a procedure, instead of passing values in as parameters, makes a procedure harder to reuse and harder to reason about — it's generally better style to pass in what a procedure needs as parameters, even if a global variable holding the same value happens to be available.
Common exam slip Don't confuse "local to the procedure" with "passed by reference." A BYVAL parameter is still local — it's a variable that belongs only to the procedure — it's just that its initial value was copied in from the caller. Locality is about where a variable can be accessed from; passing mode is about whether changes propagate back to the caller.
07

Tracing a procedure call: Swap

The classic example for BYREF is a procedure that swaps the values of two variables. This only works if the procedure can reach the caller's actual variables — a BYVAL copy would be swapped internally and then thrown away when the procedure ends, leaving the caller's variables untouched.

pseudocode
PROCEDURE Swap(BYREF X : INTEGER, Y : INTEGER)
   DECLARE Temp : INTEGER
   Temp ← X
   X ← Y
   Y ← Temp
ENDPROCEDURE
Read the brackets carefully Only X has BYREF written in front of it — so is Y passed by value? Section 8.3 of the Cambridge pseudocode guide states that when several parameters share the same passing method, the keyword doesn't need to be repeated. Since Y immediately follows a BYREF parameter with no keyword of its own, Y is also BYREF — the whole point of this procedure only works if both parameters are references to the caller's variables.
