01

Why this matters

Standard ASCII was designed in the 1960s around American English: uppercase and lowercase letters, digits, and basic punctuation. It has no way to represent é, 中, Ω, or 😀. As computing became global, that limitation became a real problem — and the industry's first attempt to fix it (extended ASCII) created almost as many problems as it solved.

02

The limits of ASCII

Standard ASCII uses 7 bits, giving exactly 128 possible codes. Every one of those codes is already spoken for: control characters, digits, punctuation, and the 52 upper/lowercase English letters. There's no room left for anything else — no accented letters, no other alphabets, no symbols beyond basic punctuation, and no emoji.

03

Extended ASCII & code pages

The obvious fix: ASCII was only using 7 of the 8 bits in a byte. Switch on that 8th bit, and you double the available codes to 256 (0–255). Codes 0–127 stay identical to standard ASCII; codes 128–255 are free for something new.

But "something new" turned out to mean different things to different people. Various organisations created their own code pages — different assignments of characters to those upper 128 codes, usually tailored to a particular language or region.

The problem

There was never one single "extended ASCII." A byte value in the 128–255 range means something completely different depending on which code page the reading software assumes. Save a file using one code page, open it assuming another, and the text turns to garbage — an error commonly called mojibake.

05

Unicode: one standard for everything

Unicode fixes the code page problem at the root: instead of many competing, incompatible systems, Unicode is a single universal standard that assigns every character — in every writing system, plus symbols and emoji — a unique number called a code point.

Code points are written as U+ followed by hexadecimal digits. U+00E9 means exactly one thing: é, on every system, in every application, forever. No ambiguity, no clash.

Unicode currently defines well over 149,000 characters, covering Latin, Cyrillic, Greek, Arabic, Chinese, Japanese, Korean, and dozens of other scripts — plus a large and growing collection of symbols and emoji.

06

UTF-8 encoding

A code point is just a number — it still has to be stored as actual bytes. UTF-8 is by far the most widely used scheme for doing this, and its defining feature is that it uses a variable number of bytes per character:

Code point rangeUTF-8 bytes usedTypical contents
U+0000 – U+007F1 byteStandard ASCII (identical encoding!)
U+0080 – U+07FF2 bytesLatin accents, Greek, Cyrillic, Hebrew, Arabic
U+0800 – U+FFFF3 bytesMost Chinese/Japanese/Korean characters, many symbols
U+10000 and above4 bytesEmoji, rare and historic scripts
Worth noticing

Because code points 0–127 use exactly 1 byte in UTF-8, identical to the original ASCII byte values, any valid ASCII text file is automatically also a valid UTF-8 file. This backward compatibility is a big part of why UTF-8 won out over competing encodings.

08

Key takeaways

  • Standard 7-bit ASCII has only 128 codes — no room for accented letters, other scripts, or symbols and emoji.
  • Extended ASCII uses the 8th bit for 256 codes, but relies on code pages that disagree on what codes 128–255 mean — causing mojibake when the wrong one is assumed.
  • Unicode assigns one universal code point (U+XXXX) to every character in every writing system, removing the ambiguity entirely.
  • UTF-8 encodes code points using 1 to 4 bytes. Codes 0–127 use exactly 1 byte, identical to ASCII, making ASCII text automatically valid UTF-8.
